# QA 6 — 모바일 프론트엔드 연동 (Sol)

작성일: 2026-11-02. 기준: `docs/qa/00_brief.md`, `docs/ARCHITECTURE.md` v0.1.2, `harness/harness.yaml`.

**판정: 실제 HTTP QA 미완료(실행 환경 차단).** 아래 서비스 동작 문제는 HTTP로 확인한 결함이 아니라 코드·로컬 스키마에 근거한 **추정**이다. 제품 합격 판정에 사용하면 안 된다. 공장·재활용업체·운반업체의 목록 복원 API와 응답 계약부터 보완할 필요가 있다.

## 실행 환경과 증거 범위

- 지정 설정: `DATABASE_URL=postgresql+psycopg://postgres:@/masdae_qa6?host=/run/user/1000/python_PostgresServer/2bc6e585c8`, `LLM_PROVIDER=off`, 포트 `8916`.
- `psycopg.connect`로 **masdae_qa6만** 연결 시도: PostgreSQL Unix 소켓에서 `Operation not permitted`. DB 존재 여부 확인·생성·시드·변경 모두 못 함. 다른 DB에는 접속하지 않음.
- 위 환경으로 `backend/.venv/bin/uvicorn app.main:app --port 8916` 실행: lifespan의 `Base.metadata.create_all(engine)`에서 같은 오류, `Application startup failed. Exiting.`, 종료 코드 3. 서버는 기동 실패 후 종료되어 남아 있지 않음. 살아 있는 서버 PID가 없어 kill 대상 없음. `pkill` 사용 안 함.
- 실제 HTTP 시도: `curl -sS --max-time 5 http://127.0.0.1:8916/v1/health` → 종료 코드 7, `failed to open socket: Operation not permitted`. **HTTP 상태 코드나 응답 본문을 받은 것이 아님.** 이후 업무 API 요청은 실행하지 못함.
- 보조 점검: 같은 DB 설정으로 앱을 import하여 `app.openapi()` 생성(DB 연결·lifespan 실행 없음), `run_flow` 4개를 메모리에서 직접 실행. `PYTHONDONTWRITEBYTECODE=1` 사용. TestClient/ASGI 호출을 실제 HTTP로 대체 집계하지 않음.
- 로컬 관찰: OpenAPI 3.1.0, 21개 경로·22개 operation. 성공 응답 스키마 22개 모두 `{}`. `/docs`, `/openapi.json` 라우트 등록은 관찰했으나 HTTP 접근·Swagger 렌더링·CDN 로딩은 미검증.
- 이 문서만 작성했고 코드·설정·테스트 파일을 수정하지 않음. 가상 회사명으로 메모리 입력만 사용했고 개인정보·실제 업체 정보는 넣지 않음.

## 응답 모양과 화면 표시 규칙

- 필드명은 대체로 영어 snake_case. 데이터베이스 자원 id는 정수, run_id는 UUID hex 문자열, QR/폐기물코드/인계서번호는 문자열이다. 서로 다른 종류의 ID 타입은 자연스럽지만 OpenAPI 응답에 명세가 없다. 폐기물코드·인계서번호를 숫자로 변환하면 안 된다.
- 같은 자원 식별자가 생성/상세는 `id`, 등급은 `bag_id`, 콜은 `order_id`다. 공통 응답 어댑터 없이 무조건 `response.id`를 쓰면 안 된다. `grade`도 판매에서는 등급 문자열, 등급 산정 응답에서는 GradeResult 객체다. DTO별 타입이 필요하다.
- 통과증 불발급은 pass_id·qr 키 생략, 미배정 hauler_id·인계서 미작성 칸은 null이다. 빈 목록은 배열, 없음은 null, 조건부 필드는 생략으로 구별해서 문서화해야 한다.
- 날짜 전용 시세 data.price.date는 `2026-09-10`(로컬 실행 관찰). 이력·인계서는 datetime. UTC 오프셋 일관성은 위 #12 재검증 필요. 화면은 명시된 UTC를 Asia/Seoul로 변환하고 날짜 전용 값에는 시간대 변환을 적용하지 않는 규약이 필요하다.
- 생성 응답에만 붙은 guide/advice/checklist는 run_id를 알아야 재조회할 수 있다. 주문/판매 상세에서 관련 run_id를 찾는 연결 정보도 필요하다.

다음은 **프론트 표시 문구 제안**이며 서버가 label을 반환한다는 뜻이 아니다. 상태 목록은 contracts와 실제 코드 대조 결과다.

| 대상 | 값 | 화면 문구/동작 제안 |
|---|---|---|
| 마대 | registered / graded / rejected | 등록됨 / 통과증 발급 / 통과증 미발급(등급 사유 표시). rejected가 판매 계약의 disputed와 혼동되지 않게 구분 |
| 판매 | posted / bundle_wait / sold / withdrawn | 판매 중 / 모아서 팔기 대기 / 주문됨 / 판매 내림. withdrawn 변경 API는 없음 |
| 주문 | ordered / payment_held | 주문 접수 / 결제 보류(시연용 가짜 결제). ordered는 생성 요청 내부 단계 |
| 주문 | dispatched / picked_up / arrived | 배차 완료 / 수거 완료 / 도착·검사 대기 |
| 주문 | confirmed / settled / rated | 검사 합격 / 정산 완료(시연) / 양쪽 평가 완료. confirmed는 검사 성공 요청 내부에서 settled로 진행 |
| 주문 | disputed / cancelled | 검사 불합격·처리 대기 / 취소됨. disputed 후속 처리와 취소 API는 P0 밖 |

상태 값만으로 버튼을 결정하면 역할/소유/인계서 준비/내 평가 여부를 놓친다. 예를 들어 settled라도 인계서 번호가 없으면 별점을 쓸 수 없다. `allowed_actions`와 불가 사유를 내려주거나 역할별 행동 조건을 정식 계약으로 제공하는 것이 좋다. 미지의 새 상태는 원문 노출 대신 ‘상태 확인 필요’로 처리한다.

## 실시간 갱신 가능성

실제 지연·누락·동시 수락은 미검증이다. 푸시는 계약상 P0 밖이며, 코드에는 SSE/WebSocket도 없다.

1. 운반 앱 전경에서는 `GET /v1/calls` 주기 조회 후 order_id 집합 차이로 새 콜을 감지할 수 있다. 이 방식은 받은 알림 이력·오프라인 알림·백그라운드 푸시를 보장하지 않는다.
2. 세 앱 모두 알고 있는 order_id는 `GET /v1/orders/{id}`를 폴링하여 status/history를 비교할 수 있다. 그러나 공장에 새로 들어온 주문 id 발견과 캐시 유실 복구에는 내 주문 목록이 먼저 필요하다.
3. 이력은 전이 정보이며 SSE 이벤트가 아니다. 목록 응답에 updated_at/version, cursor 기반 변경 조회, 영속 알림 목록을 추가하면 폴링 중복·누락을 줄일 수 있다. 폴링 간격·재시도·백그라운드 정책은 부하 시험 후 결정해야 한다.
4. 푸시 도입을 뒤로 미루더라도 신규/변경 조회와 알림 읽음 처리는 서버에 있어야 한다. 앱 로컬 저장만으로 세 기기와 재설치 시점을 맞출 수 없다.

## RunResult 화면 적합성: 로컬 직접 실행 관찰

HTTP 응답·DB 저장 성공·네트워크 전송량을 측정한 것이 아니다. 가상 공장, pp 97kg+pe 3kg, 단가 300원/kg, 주변 판매 없음으로 `run_flow`를 직접 실행했다. UTF-8 JSON을 `ensure_ascii=False,separators=(',', ':')`로 직렬화한 크기이며 HTTP 포맷/압축에 따라 달라진다. 네 flow의 모든 AgentResult.ok는 true, llm은 provider=off·available=false였다.

| flow | RunResult 바이트 | summary 글자 수 | public_claims 수 | events 수 |
|---|---:|---:|---:|---:|
| profile_company | 2,244 | 104 | 1 | 6 |
| grade_bag | 2,723 | 94 | 2 | 8 |
| listing_advice | 8,809 | 527 | 6 | 10 |
| deal_check | 3,697 | 222 | 3 | 6 |

- 사람용: `summary`와 `public_claims[].text/level/evidence`. 판매 추천에는 시세·모아서 팔기·소각비 절감 추정·판매 참고액이 별도 문장으로 나와 카드로 나누기 좋다. 출처 날짜·추정 배지를 유지해야 한다.
- 기계용: `results`에서 agent_id로 찾고 `data` 사용. grading.data.grade는 순도 0.97·A·hazard=false, vision.data.composition은 구성비, economics.data.incineration/sale은 비용/판매 참고액 범위였다. 위치 기반 배열 인덱스에 의존하면 안 된다.
- 체크리스트의 recycler_permit.ok=true, hauler_permit.ok=null, handover_entry.ok=null을 관찰했다. null은 ‘확인 필요’로 표시해야 하며 false/허가 없음으로 치환하면 안 된다. 영어 item 코드의 한국어 label 매핑도 필요하다.
- `results[].claims`를 그대로 공개하면 차단된 주장까지 그릴 위험이 있으므로 안내 문장은 public_claims/summary를 사용한다. 카드용 data에는 claim과 같은 공개 허용 메타데이터가 없어 공개 범위 계약을 별도로 정해야 한다.
- events는 실행 순서/진단 정보이며 사용자 콜·주문 알림 스트림이 아니다. 기본 카드에는 노출할 필요가 없다. 샘플에서 run_id·summary·summary_source·public_claims·llm만 추리면 판매 추천은 3,981바이트였다. 이를 즉시 필수 최적화로 판단할 크기 증거는 없다.
- 에이전트별 data 응답 스키마, 카드 label·단위·날짜·출처, 실패/일부 결과 없음 표시를 명세해야 한다. grade_bag HTTP 응답은 전체 RunResult 대신 grade·run_id를 주도록 되어 있어 화면별 로딩 방식도 다르다.

## 실제 HTTP 재검증 순서(미실행)

소켓 사용 가능한 동일 작업 환경에서 **masdae_qa6/8916/off**를 유지하고 다음을 실행해야 이 QA를 완료할 수 있다. 소유하지 않은 서버/DB는 사용하지 않는다.

1. health·docs·openapi.json을 GET하고 content-type/상태/스키마/Swagger 실행을 기록한다.
2. 가상 공장·재활용업체·운반업체·운영자를 `POST /v1/companies`로 만들고 역할별 id를 기록한다. 운영자 헤더로 재활용업체·운반업체 verify. 이후 각 요청에 해당 `X-Company-Id` 사용.
3. 공장에서 PP 97/PE 3 마대 생성·등급 → now 판매와 별도 마대의 bundle 판매 생성. 공개 목록과 내 마대·판매·상세 경로 유무를 실제 HTTP로 점검한다. 미구현 후보 URL의 404/405는 분리해서 기록한다.
4. 재활용업체가 now 상품 주문 → 공장 주문 발견 시도 → 운반 calls 조회·수락 → calls 재조회·수락 이력 복원 시도. 세 당사자의 주문 상세를 비교한다.
5. 배정 운반업체가 상세 bag_ids 기준으로 pickup·arrive, 재활용업체 inspect 합격 → 세 역할 상세/날짜/정산 확인 → 인계서 3칸·번호 → 양쪽 별점 → 재접속 시 목록/평가 여부 복원 확인. 별도 거래에서는 inspect 불합격도 확인한다.
6. 오류 입력·누락 헤더·타사 접근·없는 id·중복 수락으로 400/401/403/404/409 실제 본문을 수집한다. 등록 성공 응답을 화면 DTO와 비교하고, 페이지 파라미터가 적용되는지 다건 데이터로 확인한다.
7. POST의 RunResult와 agent-runs GET을 비교하고 크기·부분 실패·공개 주장 노출을 확인한다. 주문 상태 폴링·콜 집합 변경을 실제로 관찰한다.
8. 시작할 때 기록한 자기 서버 PID로만 종료한다. 실행 결과로 본 문서의 ‘추정’을 갱신한다.

## 좋았던 점 3개

1. 계약과 코드에서 주문 상세·상태 이력·인계서 조회가 구분되어 있어 id를 확보하면 거래 타임라인 화면의 기본 틀이 있다(HTTP 미검증).
2. 로컬 off 실행에서도 등급·추천·체크리스트가 나오고, summary와 계산 data·근거·추정 수준이 분리되어 있다.
3. 요청 DTO에 역할 enum, 양수 무게·가격, 필수 목록 제약이 있고, 공개 판매/허가별 콜의 목록 기준이 단순하다. 입력 폼과 빈 화면 설계의 출발점이 명확하다(HTTP 미검증).

## 가장 먼저 고칠 것 3개

1. 내 마대·내 판매·내 주문·내 운송 목록과 상세를 제공해 재접속 후 화면을 복원하게 한다.
2. 성공 응답 DTO·실제 오류 코드/형식·UTC 날짜·상태별 행동을 OpenAPI 계약에 넣어 앱 타입과 버튼을 확정한다.
3. 내 회사 승인 상태와 주문/콜 변경을 다시 조회할 수 있게 하고, 영속 알림함·읽음 상태를 제공한다.

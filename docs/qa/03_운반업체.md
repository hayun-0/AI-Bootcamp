# QA 03 — 운반업체(배차 담당·기사) 시점 (2026-11-02)

환경: 서버 포트 8913, DB masdae_qa3, LLM_PROVIDER=off. 가상 회사만 사용. 실제 HTTP(httpx, 스레드 동시 요청). 서버 종료 완료.
스크립트: scratchpad/qa3.py, qa3b.py (재현용)

## 확인된 사실(문제 없음)
- 콜 목록: 미확인 hauler 403, 허가코드 틀림/없음 -> 빈 목록 200, 맞는 허가 -> 목록, 공장·헤더없음 403/401. (확인)
- 동시 수락: 3곳 동시 x 6회 모두 정확히 1곳만 200, 나머지 409, 이력 dispatched 1건. 같은 hauler 4개 동시 수락도 1건만. (확인)
- 같은 콜 두 번 수락(같은 hauler): 두 번째 409, 운임 덮어쓰기 없음. (확인)
- 남의 주문 pickup 403, 남의 주문 조회·인계서 조회 403, 남의 칸 인계서 403. 수거 전 arrive 409, 수거 전 carrier 인계서 409. (확인)
- 무게 0/음수/NaN/누락/중복/미지의 bag_id/다른 주문 bag_id 모두 400. (확인)

## 계약서 대비 판정
- 검사 순서(401->역할->404->당사자->409->400) 대체로 준수. 단 pickup의 조건 순서는 계약대로.
- "먼저 수락 1곳만 409": 통과.
- 결제 보류 주문에 pickup -> 403(배정 전): 계약서 예시와 일치.

## 좋았던 점 3
1. 수락 경쟁이 조건부 UPDATE라서 3곳 동시 6회 모두 승자 1명(확인).
2. 상태 전이표 강제와 이력(order_history) 기록, 남의 주문·남의 칸 403이 일관됨.
3. 무게 입력 검증(0·음수·NaN·누락·중복·남의 마대)이 한 규칙으로 막힘.

## 가장 먼저 고칠 것 3
1. pickup/inspect 무게 검증: 등록 kg 대비 허용 오차, pickup vs inspect 차이 표시, pickup도 조건부 UPDATE로 중복 방지(#1, #2).
2. 운임 상한/INTEGER 범위(#3)와 콜 목록에 예상 운임·폐기물명·거리 표시, 운임 합의 구조(#5).
3. 배차 후 노쇼 대응(취소·재배차·타임아웃) 및 vehicle_no 검증과 번호 발급 후 잠금(#4, #6).
